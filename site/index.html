ResumeForge

A resume-tailoring pipeline and a companion Chrome autofill extension. Deterministic C# scores your knowledge base against a job posting and fills out application forms from it; a language model is only invoked for the handful of decisions that genuinely require judgment.

Token spend scales with the number of decisions being made, not with the amount of text already written. That's one rule, applied independently to two different subsystems: tailoring a resume, and filling out a form.

The cost argument

Do everything determinism can do first

The naive way to tailor a resume with a model is to hand it the whole resume and the job posting and ask for a rewrite back. Every bullet you didn't change still has to be regenerated — and billed — because a complete document has to come back out. Do that across two dozen applications and you've spent most of your token budget having your own unchanged sentences read back to you.

ResumeForge scores the resume against the job posting in deterministic C# first — BM25 relevance, skill overlap, recency — and only asks the model to make the decisions a human editor would actually make: what to include, what order to put things in, which pre-written phrasing to use. The model's output is a short list of commands, not a resume, so its cost is bounded by the number of decisions, not by how much resume exists to describe. The same move — resolve everything determinism can resolve first, spend the model's budget only on the genuine residue, cache the result so you never pay for the same judgment twice — shows up again in the autofill extension, applied to a completely different problem.

How tailoring works

The model emits commands, not prose

score-experience, score-projects and score-skills run BM25 relevance scoring plus a skill-overlap term and a recency term over your knowledge base — plain C#, no model call, producing a pre-scored candidate set of bullet IDs and requirement matches. Only after that does anything reach the model, and what it receives is a compact brief: requirement text plus truncated candidate snippets, built by build-brief from all three scoring nodes' output.

The model's entire output surface is a JSON array of commands, discriminated by an "op" field, applied by deterministic C# to the canonical resume document: 

[
  { "op": "exclude", "targets": ["exp:cascade-analytics", "prj:tinyorm"] },
  { "op": "order", "parent": "exp:nimbus-systems",
    "order": ["exp:nimbus-systems#0", "exp:nimbus-systems#2"] },
  { "op": "selectVariant", "target": "exp:nimbus-systems#0", "variantIndex": 0 },
  { "op": "emphasizeSkills", "skills": ["go", "csharp", "kafka"] }
]

exp:nimbus-systems, exp:cascade-analytics and prj:tinyorm are IDs from the sample knowledge base this repo ships in profile/ — the model never receives or emits resume prose it doesn't have to; it references content by ID instead of restating it.

Eight commands, one of which writes prose

The full command vocabulary — ResumeForge.Application.Tailoring.TailorCommand
opWhat it does
include / excludeFlip an entry's or skill group's Included flag, or remove a bullet / individual skill from its parent's list.
orderReorder a parent's children; anything omitted keeps its relative position after the listed ones.
selectVariantPick an existing pre-written phrasing from the knowledge base. Zero generation tokens — always preferred over rewrite when a suitable variant exists.
rewriteThe only command that emits prose. ≤300 characters, single line, must pass the anti-fabrication check, capped at MaxRewrites (default 6) per run.
setSummaryReplace the resume's summary block.
emphasizeSkillsFlag normalized skill names for visual emphasis.
setSectionOrderReorder the resume's top-level sections.

Validation runs before anything is applied

A command is rejected, not silently clamped, if it fails validation — ICommandValidator reports every rejection with a reason and a stable code:

unknown-target duplicate-order-entry rewrite-too-long rewrite-multiline fabricated-metric rewrite-limit-exceeded

The anti-fabrication check (IFabricationGuard) is deterministic string comparison, not another model call: it extracts number-like tokens (digits, percentages, 3x-style multipliers, identifiers like p99) and proper-noun-like tokens (capitalized words) from both the original bullet and the rewrite. A rewrite is rejected if it introduces a number that wasn't in the original, or if the original bullet had a number or a proper noun and the rewrite keeps neither. The model can re-angle a bullet; it cannot invent a metric that passes validation.

verify-fabrication and verify-coverage — the two nodes downstream of validation, run concurrently with each other — are this same kind of deterministic check, not additional model calls: one re-verifies accepted rewrites against the guard, the other computes how much of the job's requirements the tailored document actually evidences.

Concurrency and failure isolation

The graph executor (ResumeForge.Application.Graph) runs every node whose dependencies are satisfied immediately, with no artificial wave-by-wave barrier, capped by GraphOptions.MaxConcurrency. A failed node marks its transitive dependents Skipped and the run still returns a partial result with the full trace — unless the node is declared Critical, in which case the run fails outright. fetch-jd, load-kb, propose-commands, validate-commands and execute-commands are the five nodes marked critical in the tailoring graph; a JD that fails to fetch legitimately shows up as cascading Skipped statuses downstream, not a crash. Cycle detection runs once, at graph-build time.

The autofill extension

A three-tier cascade, and it never touches Submit

The Chrome extension (Manifest V3) fills job application forms from your profile using the same cost discipline as tailoring: resolve everything free tooling can resolve, spend the model only on the genuine leftovers, remember the answer.

Tier 1 — free

Board adapters

Declarative selector maps in extension/src/adapters/ for five boards — Greenhouse, Lever, Ashby, Workday, SmartRecruiters. Matches by hostname, maps canonical field keys straight to CSS selectors. No text scoring, no model call.

Tier 2 — free

Heuristic matcher

Whatever the adapter didn't cover is scored against a canonical key synonym table using label text, name/id/autocomplete attributes, placeholder and aria-label, via normalized token overlap. Accepted at confidence ≥0.72; below that, left for tier 3 rather than guessed at.

Tier 3 — one call

Model fallback, cached

Whatever's still unresolved — usually a handful of fields — is batched into one request to POST /api/autofill/resolve. The response is persisted as a LearnedFieldMap keyed by (host, formSignature); the same form's next visit resolves it for free.

Form-filling tools have a deservedly bad reputation. This one is built the opposite way, and it's enforced in code, not just documented: extension/src/content/fill.ts gates every write path — text inputs, selects, radio groups, file inputs — through hasUnprotectedUserValue, which refuses to touch a field that already holds a value the extension didn't write itself. There is no code path in fill.ts that clicks a Submit, Apply or Continue control; the file's own docstring on applyFieldValue states it plainly: "this function never submits a form and never clicks a button." Every proposed value is shown in a per-field accept/reject preview before it touches the page's DOM — you submit every application yourself.

The canonical field-key set is closed and shared verbatim between the backend (ResumeForge.Application.Autofill) and the extension (extension/src/contracts.ts) — things like firstName, email, linkedin, workAuthorization, desiredSalary. Nothing resolves to a key outside that list, and a value of null means "leave this field alone," never "fill it with an empty string."

Runs with no API key

The offline path is the default, not a fallback bolted on later

ServiceCollectionExtensions.AddAi checks for ANTHROPIC_API_KEY at startup. When it's absent, the container resolves HeuristicLanguageModel — no network call, ranking rules only: include the top-scored candidates, pick the best-matching pre-written variant, order by relevance score, never write a rewrite command. It satisfies the same ILanguageModel interface the real client does, so the rest of the graph — validation, the fabrication guard, coverage analysis, rendering — runs completely unaware of which one answered.

This means a stranger can clone the repo, run dotnet run --project backend/src/ResumeForge.Api with nothing configured, and watch the full tailoring pipeline execute end to end against the sample knowledge base checked into profile/. It's also what the backend's own test suite runs against by default.

Architecture

Four layers, one frozen contract

The backend is Clean Architecture in four projects, dependencies pointing inward: Domain (records, EntityId, the resume model — no dependencies of its own), Application (use cases, the graph engine, scoring, command validation — declares the ports it needs), Infrastructure (EF Core, markdown I/O, QuestPDF rendering, the language model clients — the only layer that knows any of those exist), and Api (ASP.NET Core minimal APIs, the composition root). The React frontend and the Chrome extension are separate projects that talk to the API over HTTP — neither links against the backend directly.

All three surfaces were built against docs/CONTRACTS.md, a single markdown file that's the frozen source of truth for every type crossing a component boundary: wire format rules, the canonical resume model, the command protocol, the graph engine's node interface, the autofill contracts, all in one document that backend, frontend and extension code are expected to match exactly.

Swappable model cores

The language model port has exactly three implementations, chosen at composition time and split by wire format rather than by vendor, since most hosted and local providers speak OpenAI's chat-completions format:

auto is the default and resolves in order: DEEPSEEK_API_KEY set → deepseek; else ANTHROPIC_API_KEY set → anthropic; else heuristic. auto never selects lmstudio — that requires a server the user deliberately started, and probing the network during DI registration isn't acceptable; selecting it is explicit.

OpenAiCompatibleLanguageModel

Serves the deepseek, openai and lmstudio presets, and any other OpenAI-format endpoint via config alone. Structured output degrades through three strategies — forced tool call, JSON-schema response format, prompted JSON — remembering whichever one worked for the process lifetime, so the cost is one probe, not one per request.

AnthropicLanguageModel

Serves the anthropic preset. Messages API, structured output forced via tool_choice on a single emit_result tool.

HeuristicLanguageModel

No network. Used by auto when no key is present, and in every test. The whole product works end to end on this implementation alone.

A CachingLanguageModel decorator wraps whichever core is selected, keyed on a SHA-256 of (ModelId, System, User, SchemaName) — ModelId carries the resolved provider and model, so switching cores can never serve a cached response from a different model.

Quick start

Nothing to configure to try it

Prerequisites: .NET 10 SDK, Node 20+.

# Backend — http://localhost:5217, applies EF Core migrations automatically in Development
dotnet restore
dotnet run --project backend/src/ResumeForge.Api

# Frontend — http://localhost:5173, proxies /api to the backend above
cd frontend
npm install
npm run dev

# Extension
cd extension
npm install
npm run build
# then load the build output as an unpacked extension via chrome://extensions

No API key needed — without ANTHROPIC_API_KEY set, the backend registers HeuristicLanguageModel and the pipeline runs fully offline against the sample knowledge base in profile/. Point your browser at http://localhost:5173, or the API's Scalar docs at http://localhost:5217/docs.
